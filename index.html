02 · 项目概要

这个项目要解决什么

按「玩家承诺 / 约束 / 我的角色 / 成功标准」四项写清楚。

玩家承诺

原版的装备是固定的，拿到就定型。这个模组让每一件掉落都随机生成：底子、补正、属性、稀有度和词条各不相同，玩家可以围绕词条搭流派，通关后还有难度阶梯、斗技场试炼和无尽试炼可以继续刷。

约束
  • 没有游戏源码和官方编辑器：只能改数据表（regulation 参数）、事件脚本（EMEVD）、角色行为脚本（HKS），再加注入的运行时 DLL。
  • 游戏版本更新会改内存布局，需要同时支持 2.7.1 和 2.7.2。
  • 要和敌人随机器、无缝联机等其他模组共存。
  • 玩家大多是普通中文玩家：解压、点「启动」就要能玩，出错要能自动收集诊断信息。
我的角色

个人项目。我负责玩法与数值设计、需求拆解和取舍、方案验收与测试、打包发布、宣传视频、玩家反馈整理。代码实现大量借助 AI 编程助手（Claude Code）完成，详见文末声明。

成功标准
  • 玩家能从开局稳定玩到通关后，存档不丢、不卡关。
  • 强度有模型可查，调数值不只靠手感。
  • 反馈能快速进版本，每次更新都有玩家看得懂的更新日志。

04 · 系统设计

五块核心系统

配色沿用游戏里的稀有度：灰（普通）、蓝（稀有）、紫（史诗）、金（传说）。

SYSTEM 01

装备生成与鉴定

敌人和宝箱掉的是「未鉴定物品」，鉴定时在游戏里当场生成一件新装备：随机底子、补正、属性、稀有度和词条。配套一键鉴定、定向鉴定、许愿石，以及装备工坊里的词条继承、武器重铸、超限锻造。

  • 运行时生成
  • 游戏内界面
  • 存档内记录
SYSTEM 02

词条系统

157 个词条族。数值类直接写进游戏数据；命中触发、附近触发和改变规则的机制类词条（64 个）由运行时 DLL 的规则引擎实现。中文说明按原版护符的写法，带具体数字；触发时有对应的光效反馈。装备工坊里有词条百科可查。

  • 规则引擎
  • 事件总线
  • 触发反馈
  • 词条百科
SYSTEM 03

掉落与数值

敌人按所在地区分强度档，掉落表按档位复制；稀有度概率随档位提高，观察力只影响掉落数量。敌人随机时按地区补血量。离线数值模型用蒙特卡洛模拟整个流程，输出各难度相对原版的强度曲线和词条强度排名。

  • 分档掉落
  • 蒙特卡洛模型
  • Python → Rust
SYSTEM 04

难度与终局

多档局内难度，敌人血量、攻击、抗性和掉落随难度变化。「死亡」以上难度有改版头目、魇化精英和咒痕；七道咒痕可以逐一反转成祝福。另有斗技场试炼、无尽试炼、暗黑商店分阶段解锁、卢恩银行和死亡惩罚。

  • 难度阶梯
  • 终局循环
  • 风险与回报
SYSTEM 05

工具与管线

启动器（Python + WebView2 网页界面）负责每局数据生成、启动游戏、存档定时备份、在线和离线更新、崩溃检测与诊断包导出。开发侧有游戏内测试面板、帧耗时统计和数值模型。

  • 一键生成
  • 诊断包
  • 增量更新
  1. 启动器玩家点「启动」或「重新随机」，读取难度和设置。Python · WebView2
  2. 生成游戏数据读原版数据表，生成装备底表、掉落表、词条、事件脚本、行为脚本和中文文本。多进程并行
  3. 叠加加载不改游戏目录，启动时由注入式加载器把改动叠上去。regulation · EMEVD · HKS · msg
  4. 运行时鉴定时生成装备，规则引擎每帧处理机制词条，游戏内界面提供装备工坊。Rust DLL · hudhook
  5. 反馈崩溃时自动导出诊断包，玩家在反馈表登记，进入下一个版本。诊断包 · 反馈表

新版本通过在线或离线增量更新包发给玩家，旧存档里的装备随版本一起迁移。

四个迭代案例

案例 1 · 词条设计

「千钧」：一个改变规则的传说词条，五轮迭代

设计意图

戴上传说护符「千钧」后，满蓄力重击一定能打崩敌人架势，让「蓄力重击流」成立；代价是其他攻击不再削减强韧度。

约束

游戏只在命中那一刻判定是否崩架势，引擎改不了，只能每帧读写敌人的强韧度；扫描周围敌人有每帧开销。

  1. v0.72026-10-30
    上线
    满蓄力一出手，身边敌人的架势全部压低；头目改为削减强韧度上限的 30%。
  2. v0.8.111-01
    决定
    「千钧」「见切」「猎印」这类要看周围敌人的词条，改成只在戴着时才每帧扫描，没戴不花开销。
  3. v0.8.511-01
    观察
    没打中的敌人也被压架势，不合直觉；头目不挨打时架势很快回满；拉塔恩这类头目不在游戏的「周围角色」列表里，完全吃不到效果。
    决定
    改为打中才生效。因为引擎只在命中瞬间判定，所以出手时先扣头目强韧度上限的 30%，打中时连同这一击的削韧一起结算，没打中就加回去；扣掉的部分保持 15 秒不回；头目另外补进「周围敌人」。
  4. v0.10.511-13
    决定
    削减比例从 30% 提到 40%；满蓄力出招时身上泛起削韧的光，让玩家看得到触发。
  5. v0.10.1611-20
    观察
    玩家反馈：连招里连续两下满蓄力，第二下常常不扣；明明打中了，先扣的强韧度有时又加回去；体型很大的头目有时不扣。
    原因
    蓄力标记跨招式残留；「这一击」的结算窗口关得太晚；距离没有减去敌人的碰撞半径。
    决定
    每次新的蓄力开始时先结算上一击；命中判定加上「强韧度下降」和「崩架势」两种信号；距离按体型修正；把连续蓄力的场景写成单元测试。
复盘

「先扣后打」是被引擎判定时机逼出来的方案，玩法上成立。后面几轮问题都出在「一击从哪开始、到哪结束」没定义清楚。v0.10.16 把这个边界写进了测试，之后再改这条规则可以先跑测试；游戏内的最终效果还在等玩家确认。

案例 2 · 工程与玩家信任

启动器被安全软件拦截：先改特征，再换掉根源

问题

部分安全软件（如火绒的「系统加固」）在玩家打开启动器、点按钮、崩溃检测时弹出「利用 PowerShell 执行可疑脚本」，玩家会以为整合包带毒。

约束

不能要求玩家去改安全软件设置；启动器同时负责启动、数据生成、诊断包和更新，不能停更去重写。

  1. v0.10.72026-11-14
    决定
    先去掉最像恶意脚本的几个特征：不再隐藏窗口启动、不再传编码过的命令、不再从系统临时文件夹运行；诊断包也不再读取杀毒软件的记录。
  2. v0.10.1411-18
    观察
    仍有安全软件把整合包误报成病毒。
    决定
    启动器整体从 PowerShell 改写为 Python（随包带运行环境）+ WebView2 网页界面，不再经过 Windows 的脚本程序；界面和用法保持不变；去掉「经典界面」，只维护一套。旧脚本保留下来做对照测试。
    结果
    触发这类拦截的条件（运行 PowerShell 脚本）不再存在；玩家不需要重新学习操作。
复盘

第一次只改了特征，规则一变就可能再被拦。第二次的迁移成本高得多，但处理的是根源。以后遇到「玩家信任」类问题，会更早评估是否直接换掉触发条件。

案例 3 · 数值

数值曲线：从「感觉偏强」到可以重跑的模型

问题

随机装备、157 个词条和敌人随机叠在一起，强度没法靠手感判断；前身项目留下的强度模型基于旧数据，已经不准。

约束

模型必须和游戏里生成装备的逻辑一致，否则结论没有意义；改一次数值后要能很快重跑。

  1. 搭建2026-10-30
    做法
    直接调用游戏内鉴定用的同一份 Rust 代码导出装备池（每类每档 400 件），用蒙特卡洛模拟一个角色按流程拿装备、配装、打敌人；对比「原版 / 不随机敌人 / 随机敌人」三种模式，输出强度曲线和词条强度排名。
    提速
    Python 版 200 轮要 575 秒，移植到 Rust 后 20 秒；两版的词条排名一致，其余差异在随机种子误差以内。
  2. v0.911-04
    观察
    模型显示到幽影之地后期，近战强度约为原版的 12 倍，法术只有 2～3 倍。
    决定
    生成的法杖、圣印记补正乘一个随机倍率：普通 0.7～1.3、稀有 0.9～1.5、史诗 1.1～2.1、传说 1.5～2.5，越靠中间越常见。
  3. v0.9.711-06
    决定
    法球类词条的伤害改为按手上法器的法术补正计算，强化、补正和加点都会影响。
  4. v0.10.1811-21
    决定
    弓也加上按稀有度定范围的补正倍率，远程流派跟上。
未解决 / 下一步

0.10 版的反馈里仍有「前期成型速度太快」。模型现在看的是全流程曲线，开局几个小时的掉落节奏还没有单独校准，这是下一步要补的。

案例 4 · 兼容与取舍

兼容第三方敌人随机器：先保证玩家不卡关

问题

开敌人随机时，唤灵蜗牛被换到尤米尔的头目场地，两只随从打完只亮血条，蜗牛本体不出现，战斗结束不了。

约束

敌人随机由第三方随机器生成，不随整合包分发，我们只能改交给它的预设；诊断包里没有那一份事件脚本。

  1. 排查2026-11-20
    观察
    运行日志显示蜗牛在场地里，但从没被激活。外部报告提出的两个原因，对照参数后都排除了。更可能的原因是随机器合并事件时套用了场地模板，关掉了它的 AI 和碰撞，但没有那一局的事件文件，无法证实。
  2. v0.10.1611-20
    决定
    在随机器预设里让两只唤灵蜗牛不再被换走，它们原来的场地照样换成别的头目。损失两只头目的随机性，换来不会卡关。
复盘

根因还没证实。先用最小的改动止住卡关，把排查记录留下，排除掉的方向不再重复追；等拿到能复现的那一局数据再回头处理。

08 · 整体复盘

32 天、58 个版本之后

做得好的
  • 发布节奏快，每个版本都有面向玩家的更新日志，写法避开开发术语。
  • 数值模型和游戏共用同一份生成代码，结论可以直接落到数值改动上。
  • 存档安全优先：定时存档备份、离线增量更新包、旧装备随版本迁移。
  • 崩溃时自动导出诊断包，远程排查不依赖玩家描述。
要改进的
  • 游戏内测试跟不上发布速度：不少修正只有单元测试覆盖，游戏内效果靠玩家确认。
  • 和其他模组、叠加软件的兼容问题定位慢：第五护符槽偶尔不生效，根因未明，目前靠运行时补挂兜底；部分玩家打不开装备工坊，已定位到界面钩子被帧数显示类叠加软件抢占，尚未修复。
  • 前期强度节奏仍有反馈，模型还没覆盖开局阶段。
